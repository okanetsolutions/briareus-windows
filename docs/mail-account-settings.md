# Mail account settings (#123, epic #120)

Mail is global navigation beside the sessions list and is also available under Settings → Mail account settings. It requires an Admin token and a deployed OpenAPI catalog advertising `GET /settings/mail/accounts`; each action additionally requires its own method/path. Older servers and read/manage tokens have no Mail navigation or actions. No message reading routes are registered here: the inbox is issue #124.

The server's `providers` list controls which Gmail/Outlook connections are offered. Its defaults initialize a new connection. Accounts show their label/address, provider, enabled state, sync window, connection status, message/unread counts, last successful sync and last error. Label, Enable/Disable and Sync days save immediately; the window must be an integer from 1 to 365. Changing the window starts another first sync. OAuth credentials and provider cursors are never retained in the public model, displayed or copied into update bodies.

Sign in always opens the system browser, including Gmail. For `finishesOnServer: true`, the screen polls account status every 10 seconds until a new account or the requested account's `reauth` → `connected` transition appears, or the start expires. The browser reports callback failures, including HTTP 409 for the wrong mailbox. For an already connected account, the contract offers no definitive completion identifier: read the browser's result and use **Browser finished: refresh**. A sync changing `updatedAt` is deliberately insufficient evidence of OAuth completion. Connecting an already connected mailbox without selecting its account also requires this browser confirmation.

For other redirects, use **Paste callback address** immediately after sign-in. Paste the complete final URL (not just its code); the client validates its exact redirect destination, matching single `state`, a single nonempty `code`, absence of provider error/fragment and the pending expiry, then submits only the decoded state/code to `connect/finish`. Microsoft codes may last about one minute. A failed exchange consumes the start, so start again after an expired/refused/ambiguous exchange. Wrong-mailbox 409 remains visible and explains that the original account is unchanged; sign in to that mailbox again or connect the other one separately. If the finish route is absent, a client-finished start is refused before opening the browser.

Sync now accepts the server's 202 account response as running work and polls the list every 10 seconds while any account is syncing. Failures back off to a minute (or a longer Retry-After); refresh and writes respect the rate-limit wait. 409 requires reauthentication; 503 means the provider is unavailable on the server. There is no automatic retry of writes or OAuth exchanges. Refresh account status before repeating an ambiguous write.

Disconnect requires explicit confirmation explaining that core removes its synced copy and tokens, while the provider mailbox is kept. Google/Microsoft may still list the app as having access until it is removed in the provider's account settings.

Leaving the screen cancels delivery of outstanding results, stops polling and clears local sign-in/account state; it does not revoke a sign-in already issued on the server. Results from another connection, hidden screen or changed permission/catalog are discarded. Requests use account IDs rather than list positions. Settings dialogs copy their input values before entering their nested message loop, send only the field edited and discard input if the screen is retired during the dialog; polling pauses while the app is inactive.

## Verification and release gates

Regression tests cover all six transport routes, 201/202, `accountId`, 400/401/403/404/409/429/503 with no exchange retry, provider availability, credential-free models/settings bodies, callback destination/state/duplicates/expiry/errors, account-specific completion and sync timestamp false positives, catalog/token gating, hidden/changed connection results, cancellation and conservative rate-limit delays. Required Windows CI runs GCC/MSVC warnings-as-errors, core/app tests, coverage, ASan, debug-CRT leaks, UBSan/fortify/stack protector, lint and editorconfig on the implementation PR.

Merged-contract verification is complete; deployment is confirmed by the user.
